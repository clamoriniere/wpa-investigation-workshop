# Case 06 — solution

## Root cause

The WPA does not carry `metricName` + `metricSelector` directly. It references a hand-created
`DatadogMetric` object, `case06-orders-queue`, via `external.metricName:
datadogmetric@wpa-case-06:case06-orders-queue`. That object's `spec.query` filters on `queue:orders`.
The queue was renamed to `orders-v2` a few weeks ago; the loadgen (standing in for the real service)
emits the metric with the new tag value. The saved query still asks for the old one, so it matches no
series.

## Why the report is misleading

The user's instinct — "this worked before, nothing in Kubernetes or Datadog changed" — is correct on
both counts, and that's exactly the trap. Nothing *in* Kubernetes or Datadog changed. What changed
was a tag value on the metric being submitted, on their side, and a saved query on the Datadog side
that nobody thought to treat as part of "the deploy." They mentally filed the rename as "just a
naming thing," which is true for their own code and false for a query that pins that name literally.

## How to find it

`kubectl describe wpa case06-app -n wpa-case-06`:

```
Conditions:
  Type          Status  Reason                    Message
  AbleToScale   True    SucceededGetScale         the WPA controller was able to get the target's current scale
  ScalingActive False   FailedGetExternalMetric   the WPA was unable to compute the replica count: ...
Events:
  Warning  FailedGetExternalMetric  unable to get external metric wpa-case-06/datadogmetric@wpa-case-06:case06-orders-queue/...
```

Same shape as case 02 — `AbleToScale=True`, `ScalingActive=False` — but this time there's no
`dcaautogen-*` object to go dig up, because the metric was never autogenerated in the first place.
The name in the event, `datadogmetric@wpa-case-06:case06-orders-queue`, points straight at a real,
named object:

```
kubectl get datadogmetric -n wpa-case-06
# case06-orders-queue

kubectl describe datadogmetric -n wpa-case-06 case06-orders-queue
# Spec:
#   Query: avg:wpa_workshop.orders.queue_depth{case:06,queue:orders,workshop_name:...}.rollup(30)
# Status:
#   Conditions:
#     Valid   False
#     Error   True   Unable to fetch data from Datadog
#            ... reason: missing result from reply ...
```

The `Query:` line is again the fastest way in: pasting it into a Datadog notebook returns nothing.
Comparing it against what the loadgen actually tags:

```
kubectl -n wpa-case-06 get deploy case06-loadgen -o jsonpath='{.spec.template.spec.containers[0].env}'
# QUEUE_NAME=orders-v2
```

`orders` vs `orders-v2` is the whole fault.

## The fix

```
kubectl -n wpa-case-06 patch datadogmetric case06-orders-queue --type merge \
  -p '{"spec":{"query":"avg:wpa_workshop.orders.queue_depth{case:06,queue:orders-v2,workshop_name:'"${WORKSHOP_NAME}"'}.rollup(30)"}}'
```

Or edit `query` in `workspace/case-06/wpa.yaml` (the `DatadogMetric` object is defined there
alongside the WPA) and re-apply.

## What should happen next

Once the query matches real data, `case06-orders-queue`'s `Valid` condition flips to `True`, the WPA's
`ScalingActive` follows with reason `ValidMetricFound`, and `case06-app` scales: the metric sits at
100 against an 80 high watermark, giving `ceil(1 * 100/80) = 2`, and `algorithm: average` then finds
100/2 = 50 already inside the 40-80 band. `./case.sh verify 06` checks exactly that — the shared
check doesn't care whether the metric came from an autogenerated or an explicit `DatadogMetric`.

## The lesson

A metric reference is not just a name — it is a name plus every tag in the query, and an explicit,
hand-written `DatadogMetric` doesn't get regenerated the way the Cluster Agent's `dcaautogen-*`
objects do when the underlying selector changes. When a source-of-truth value (a queue name, a
region, an environment) gets renamed, treat every saved query that filters on it as part of the
blast radius — the rename is not "just on our side" if a Datadog object has that string baked in.
`datadogmetric@<namespace>:<name>` is the same syntax an HPA would use; a WPA takes it identically.
